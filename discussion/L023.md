# L023 · FULL · SP1 Blobstream (OtterSec 2024-08, ed6d066) · OS-BSP-ADV-00 "Lack of Block Height Validation" (Critical, fixed e529c13)
## Pass 1: report only
The SP1 program takes trusted_block_height and target_block_height as separate inputs and commits them to the public outputs without checking them against the heights inside trusted_light_block / target_light_block. commitHeaderRange then commits the new header and data commitment under those heights. An attacker can record a valid header/commitment under the wrong block height.
- C1 met, C2 met (contract stores header hash and data commitment by height), C3 met (the height the consumer stores by is a public output the program never constrains).
- Same shape as L066 (Linea finalized block number in PI, unchecked). Proposed: Y, P1 (stored value effectively prover-chosen; alt OTHER like the guide's Payy extent case), PSS N, conf H.

## Pass 2: code (sp1-blobstream ed6d066; fix e529c13 "audit fixes (#18)", descendant)
- program/src/main.rs: trusted_block_height / target_block_height read from ProofInputs and committed as-is; the light blocks' own header heights are never compared. Header hashes and data commitment are computed from the light blocks.
- SP1Blobstream.commitHeaderRange: checks po.trustedHeaderHash == blockHeightToHeaderHash[latestBlock] and range of po.targetBlock, then stores blockHeightToHeaderHash[po.targetBlock] = po.targetHeaderHash and latestBlock = po.targetBlock. So a real header gets recorded under a prover-chosen height, and latestBlock advances to it. Confirmed.
- Keep: Y, P1, H.
