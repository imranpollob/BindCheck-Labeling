# L032 · FULL · SP1 Contract Call · V-SP1CC-VUL-008 "Loss of Variant Type When Converting BeaconAnchorId to U256" (Low, Fixed 9155689)
## Pass 1: report only
BeaconAnchorId::{Timestamp, Slot} both encode to the same U256 public `id`; the on-chain verifier only handles timestamps. Report impact: unexpected failure or misinterpretation.
- P5-shaped (meaning of a public input ambiguous). But a slot-anchored proof checked as a timestamp looks up a non-matching/absent beacon root, so it fails closed and the attacker can't get a wrong anchor accepted.
- Proposed: N, NA, PSS N, conf M (confirm the verifier's lookup in code).

## Pass 2: code (6ccad760ca)
- ContractCall.sol verifyBeaconAnchor(timestamp=id): reverts ExpiredAnchor if block.timestamp - id > 12*8191, else looks up BEACON_ROOTS(id). A Slot id (~1e7) is "older" than the window, so it always reverts. Fail-closed: ambiguity causes rejection, never a wrong anchor.
- Fix ed2293075d: AnchorType {BlockHash, Timestamp, Slot}.
- Keep: N, NA, H.
