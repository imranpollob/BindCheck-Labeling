# L035 · FULL · Aleph Zero Shielder (zkSecurity 2025-03, 22e2f52) · #00 "User's Account Can Be Poisoned in NewAccount and Deposit Transactions" (Medium, fixed zkOS-circuits#90 / zkOS-monorepo#210; sheet fix 719c30e)
## Pass 1: report only
depositERC20 / newAccount verify a note-transition proof and pull the deposit from msg.sender. The proof doesn't commit to the sender, so anyone who sees the pending tx can submit it first from their own (e.g. illicit) address: the deposit lands in the victim's account funded by the attacker, "poisoning" it (and the victim's own tx then fails).
- C1 met, C2 met (tokens transferred from msg.sender, note added to the victim's account), C3 met (who funds the deposit is caller-chosen, not fixed by the proof).
- Guide §1 front-running: the effect changes in the front-runner's favour (here: dumping tainted funds on a victim). Fix binds the caller into the proof. Proposed: Y, P1 (alt P2 "caller not bound"), PSS N, conf H.

## Pass 2: code (zkOS-monorepo 22e2f52; fix 719c30e "ZK-820: Commit to caller address (#210)", descendant)

- Fix adds addressToUInt256(msg.sender) as a public input in both _newAccount and _deposit. Addresses it.
