# L019 · FULL · Taiko Shasta (OpenZeppelin) · "Lack of Cryptographic Binding Between Proof and Guest Program ID" (Critical, Resolved PR #20916)
## Pass 1: report only
Risc0Verifier/SP1Verifier check that the caller-supplied blockImageId/blockProvingProgram is in the trusted mapping, then verify the seal against the aggregation program. The aggregation proof never says which inner guest program it verified, so an attacker can aggregate a malicious guest's proof and submit it with the trusted ID; invalid state transitions are accepted.
- C1 met (verifier accepts), C2 met (transition proven, then finalized), C3 met (program ID, i.e. what statement was proven, is caller-claimed, not fixed by the proof).
- GUIDE P4 lists "vk or program ID not pinned in the consumer" verbatim.
- PSS: N. The zkVMs and the recursion are sound; the gap is what the app's aggregation program exposes and what the contract checks. Debatable, since the aggregation guest is a recursion program.
- Proposed: Y, P4, PSS N, conf H (binding), M (PSS).

## Pass 2: code (taiko-mono 503445678a; fix d5b904f71f)
- Risc0Verifier.verifyProof: `(seal, blockImageId, aggregationImageId) = abi.decode(_proof, ...)`; `require(isImageTrusted[blockImageId])`; then `verify(seal, aggregationImageId, sha256(publicInput))`. blockImageId is never part of the verified statement, so it is checked for membership and then ignored. Same in SP1Verifier per report.
- Fix: journalDigest = sha256(hashZKAggregationPublicInputs(blockImageId, publicInput)), so the inner image ID is now bound. fix_addresses_flaw = Y (for Risc0; SP1 per report).
- Confirms Y, P4, H. PSS N (zkVM recursion is sound; the app's aggregation statement and the consumer check omit the program ID).
