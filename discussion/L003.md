# L003 · FULL · vlayer (Veridise, a763614) · V-VLYR-VUL-003 "Inconsistent dependencies allow injection of malicious email bodies into email proofs" (Critical, Fixed PR 2091)
## Pass 1: report only
mailparse accepts a lone LF as a header/body separator; the dkim crate hashes everything after the first CRLFCRLF. So an attacker inserts an extra MIME "body" after the headers using \n\n. DKIM still passes over the original body, but the Email returned (and exposed to the prover contract and the consumer) contains the attacker's body, which no signature covers.
- C1 met. C2 met: the app acts on the verified email body. C3 met: what the email says isn't fixed by the signed content the proof checks.
- Like the guide's Payy "extent" example: the consumer is told bytes that the check never covered. Parser differential within the guest, not a consumer/circuit encoding mismatch, so not really P5.
- Proposed: Y, OTHER (signed region ≠ region exposed as verified; parser differential), PSS N, conf M. Alternative: P5.

## Pass 2: code (vlayer a763614; no fix_commit in sheet, report cites PR 2091)

- VerifiedEmail.body is returned to the prover contract and so into the journal the app acts on. Confirmed. Keep: Y, OTHER, M.
